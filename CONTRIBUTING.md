# Contributing to go-atlas-net

Thank you for your interest in contributing to go-atlas-net! This guide will help you get started.

## Prerequisites

- **Go 1.27+** — [download](https://go.dev/dl/)
- **Make** — for running project targets
- **Git** — for version control

## Getting Started

1. **Fork** the repository on GitHub.

2. **Clone** your fork:

   ```bash
   git clone https://github.com/<your-username>/go-atlas-net.git
   cd go-atlas-net
   ```

3. **Create a branch** from `develop`:

   ```bash
   git checkout -b feat/my-feature develop
   ```

4. **Make your changes**, then run checks:

   ```bash
   make fmt
   make lint
   make test-all
   ```

5. **Commit** using [Conventional Commits](#commit-messages) and push:

   ```bash
   git push origin feat/my-feature
   ```

6. **Open a Pull Request** against the `develop` branch.

## Branch Naming

Use the following prefixes:

| Prefix | Purpose |
|--------|---------|
| `feat/` | New features |
| `fix/` | Bug fixes |
| `docs/` | Documentation changes |
| `refactor/` | Code refactoring |

## Commit Messages

We follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>[(<scope>)][!]: <description>

[optional body]

[optional footer(s)]
```

**Types:** `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `perf`, `build`, `style`, `revert`

**Scope** is optional. When present, it must be listed in [`commit_scopes.txt`](commit_scopes.txt). Never use `root`; omit the scope for
repository-wide changes. Use `!` before the colon for a breaking change; a `BREAKING CHANGE:` footer explains it and is rejected without the `!`,
because the release notes group breaking changes by the subject.

Describe the concrete change and its purpose. Keep the body only when it explains behavior or a decision beyond the subject. Do not include filler,
work logs, test results, coverage figures or validation summaries. Do not mention agents or AI assistance, add generation signatures, or add agent
co-author trailers. The same format and scope rules apply to PR titles. Merges generated by git (git flow releases and hotfixes) keep git's
subject.

Examples:

```
fix(http/client): keep the retry budget per request
feat(urlx): reject base URLs with a fragment
refactor(http/client): split the transport options
test(urlx): cover joining relative paths
docs(README): add quick start examples
build(devtools): bump golangci-lint
build(deps): bump golang.org/x/sys from 0.48.0 to 0.49.0
```

Dependabot opens its updates as `build(deps): bump …` (see [`.github/dependabot.yml`](.github/dependabot.yml)); they follow the same rules
and get no exemption.

### Automated Validation

- **GitHub Actions** automatically validates all commit messages and PR titles
- **Local validation** can be enabled with: `git config core.hooksPath .githooks`
- Run `bash .github/scripts/validate-commits.sh` to check your commits before pushing
- Run `bash .github/scripts/test-commit-validation.sh` after changing the validator or `commit_scopes.txt`

## Code Style

### Formatting

- Run `make fmt` before committing — this runs `golangci-lint fmt`, whose `gci` formatter applies the project's import ordering (`make fmt-check`
  reports without rewriting). Generated files follow the same rule: optgen writes them through `gofmt -w` and `make generate` then runs
  `golangci-lint fmt` over every `*_gen.go`; the standalone `gci` binary is not used.
- Maximum line length: **156 characters** (enforced by `lll` linter).
- `wsl_v5` enforces blank lines around blocks and statements, and `godoclint` requires a doc comment on every exported symbol.
- Test files are formatted like any other file and are linted only by
  `asciicheck`, `copyloopvar`, `goprintffuncname`, `ineffassign`, `misspell`, `modernize`, `predeclared`, `unused`, `whitespace`, `wsl_v5`;
  every other linter skips `_test.go` files. Code behind test-only build tags (`integration` and the repository's other test tags) is linted too.

### Import Ordering

Imports must follow this order (enforced by `gci` via `.golangci.yml`, in this exact order):

1. Standard library
2. Third-party packages (default)
3. `google.golang.org`
4. `golang.org`
5. `github.com/altessa-s` (other altessa packages)
6. `github.com/altessa-s/go-atlas-net`
7. Blank imports
8. Aliases

### Tests

Tests may use the standard `testing` package alone or [testify](https://github.com/stretchr/testify) (`require` for preconditions, `assert`
for independent checks); both are fine in library tests.

### Copyright Headers

All `.go` files must include the copyright header. Run `make copyright` to add it automatically.

```go
// Copyright 2021-2026 ALTESSA SOLUTIONS INC.
// Use of this source code is governed by the MIT license that can be found in
// the LICENSE file.
```

## Generated options

Package options are generated by [`optgen`](https://github.com/altessa-s/go-optgen) from the private `options` struct in each `options.go` into
`options_gen.go`. `make generate` builds the optgen and golangci-lint versions pinned in `devtools/go.mod` into `bin/`,
regenerates every package and formats the result. When a change needs a new or changed option, edit the `options` struct and its `optgen` tags in
`options.go`, run `make generate`, and commit the regenerated `options_gen.go` in the same change. Never edit `options_gen.go` by hand; CI runs
`make generate-check` and fails when the committed files are stale.

Options are only ever generated with go-optgen: do not hand-write `With…` option functions. A field may opt out with the `manual` directive
(`optgen:"manual"`) only when the generator cannot express the option, and a comment next to the field must say why.

## CI checks

CI requires at least 94% total statement coverage on Linux, counted over every package of a module by any of its tests
(`-coverpkg=./...`). Raise this floor as coverage improves; do not lower it to accommodate untested changes. The full suite runs with the race
detector and shuffled test order, generated files must match `make generate`, and
every package is cross-compiled for darwin and windows.

## Fuzzing

`go test ./...` already executes every fuzz target over its `f.Add` seeds, so seeds act as ordinary regression cases and a PR needs nothing extra.
Mutation is separate: `make fuzz` walks each target for `FUZZTIME` (`go test -fuzz` accepts one target per package per invocation), and the `Fuzz`
workflow does the same nightly with 2m per target, restoring the generated corpus between runs so coverage compounds.

Write a fuzz target when the input is attacker-controlled or there is a property worth stating — a round trip, an allowlist that must hold, an
invariant the code documents. "Does not panic" is the floor, not the goal: a target with no assertion passes for the wrong reasons. When a run
fails, Go writes the minimized reproducer to the package's `testdata/fuzz/<Target>/`; commit it, so the case is pinned forever in the seed corpus.

## Pull Request Process

1. Ensure `make lint` and `make test-all` pass.
2. Write conventional commit messages: release notes are generated from them by goreleaser at release time, there is no
   manually maintained `CHANGELOG.md`.
3. Fill out the PR template completely.
4. One approving review is required before merging.
